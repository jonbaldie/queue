# Queue exploratory testing on Linux, 2026-11-07

## Result

No confirmed bugs and no new issues. Three journeys completed through HTTP against native service processes. The pass reused the prior [2026-10-24 driver](../2026-10-24-queue/driver.py) with a new isolated state path, a termination handler, and a nonzero exit for failed checks. The [transcript](journeys.txt) records the requests' observed outcomes and process IDs. Server logs are in this directory.

## Setup

- Tested `origin/main` at `9e34878`, the merge of [release PR #198](https://github.com/jonbaldie/queue/pull/198), in a fresh worktree on Linux x86-64.
- Deno 2.7.6 was downloaded into the worktree. `deno install --frozen --lock=deno.lock --entrypoint main.ts` succeeded with a worktree-local `DENO_DIR` and `TMPDIR`. A subsequent [install recheck](install-recheck.txt) recorded exit status 0 using the populated local cache.
- Services used `deno run --frozen --lock=deno.lock --allow-net --allow-read --allow-write --allow-env main.ts`, bound to loopback with a disposable bearer token. Persistence files and scratch data stayed in `target/exploratory-2026-11-07/` in the worktree.
- The driver used explicit high rate and capacity limits for functional checks, except where it tested lower limits. Readiness required a successful public `/health` response.

## Journeys

### Publish and consume work

The README promises FIFO delivery and removal after dequeue. A user published typed values to a Unicode queue, inspected length, used `HEAD` and peek, then drained the queue. The results preserved types and FIFO order. `HEAD` and peek left the queue unchanged. The drained queue disappeared from `/queues`.

As a variation, six concurrent consumers received all 120 distinct jobs once and the final length was zero. Unauthenticated queue access returned 401 while health remained public. See [journeys.txt](journeys.txt) and [j1-server.log](j1-server.log).

### Recover pending work

With persistence enabled, the user published five jobs and consumed one. A second process using the same directory exited with an ownership error. The first server was then stopped, once gracefully and once with SIGKILL in separate fresh directories. On each restart, all four remaining jobs survived in FIFO order despite lower capacity limits. A full queue rejected another job. After draining it, a new queue accepted a job and retained it through another restart. Consumed work did not reappear.

See [journeys.txt](journeys.txt), [graceful restart](j2-0-restart-server.log), [crash restart](j2-1-restart-server.log), and [rival process](j2-1-rival-server.log). This exercises process crashes, not power loss or full-disk behavior.

### Correct input and retry at limits

Invalid JSON, null or missing payloads, unrepresentable numbers, invalid UTF-8, malformed queue-name encoding, and excessive nesting returned 400 without creating a queue. A 128-code-point queue name worked and a 129-code-point name did not. Depth and queue-count limits returned 507; retries succeeded after capacity was freed. An exactly 1,048,576-byte request was accepted and retrieved, while a 1,048,577-byte request returned 413 without increasing length.

Persisted objects at nesting depths 1,000, 2,000, and 2,999 were compared byte-for-byte before and after restart, twice with fresh directories. A separate server allowed three requests, rejected the fourth with 429, kept health available, and accepted a request after 61 seconds. See [journeys.txt](journeys.txt), [boundary server log](j3-server.log), and [rate server log](j3-rate-server.log).

## Findings and limits

No candidate checks failed, so there are no confirmed bugs or unresolved bug candidates to file. The rate and capacity checks use real time and real HTTP, not mocks. The exact-size fixture length assertions check the driver input; the response and subsequent dequeue check the service.

The pass did not exercise Docker packaging, compiled binaries, interrupted uploads, full-disk or power-loss durability, proxy deployments, or sustained-load performance. The existing [long-record recovery performance issue #194](https://github.com/jonbaldie/queue/issues/194) was not assessed. Prior ownership and interrupted-upload reports [#173](https://github.com/jonbaldie/queue/issues/173) and [#172](https://github.com/jonbaldie/queue/issues/172) were checked for overlap; this run did not repeat the interrupted-upload scenario. A 507 response does not distinguish queue depth from queue-count exhaustion in these checks. This is a usability observation, not a filed bug.

## Replay and cleanup

Run from the repository root with Deno 2.7.6 on `PATH` and a worktree-local `DENO_DIR`. The replay overwrites the transcript and server logs in this folder.

```sh
python3 docs/exploratory-testing/2026-11-07-queue/driver.py \
  > docs/exploratory-testing/2026-11-07-queue/journeys.txt 2>&1
```

Allow at least 61 seconds for the rate window. The driver registers each process for cleanup, handles SIGTERM, waits for processes to exit, and removes the scratch state directory in a `finally` block. Ports are selected by binding and releasing an ephemeral port before startup, so a port race is possible. No collision occurred in this run. A second SIGTERM during cleanup could interrupt cleanup itself; no termination interrupted this run. The [teardown record](teardown.txt) shows that the registered process IDs and ports were absent after the run. No Docker containers, images, volumes, or browser sessions were created.
