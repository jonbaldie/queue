## Journeys exercised

### 1. Core FIFO, Multi-Queue Isolation, Payload Fidelity & Edge Values

- **Health check probes**: Verified `GET /health` and `HEAD /health` return `200 OK` with `Content-Type: application/json` without authentication. Verified documented `/health/` trailing-slash variant also succeeds.
- **Initial state**: Checked `GET /queues` returns `[]`.
- **Payload types & fidelity**: Enqueued varied payloads to queue `orders`:
  - Strings: ASCII (`"order-101"`), Unicode emojis and accents (`"🔥 rocket 🚀 ñoño"`), empty string (`""`), and multiline strings with newlines (`"line1\nline2\r\nline3"`).
  - Numbers: zero (`0`), negative zero (`-0`), positive integers (`42`), negative integers (`-42`), floating-point values (`3.14159`), positive scientific notation (`1e5`), negative scientific notation (`1e-5`), and JavaScript safe integer boundary `Number.MAX_SAFE_INTEGER` (`9007199254740991`).
  - Booleans: `true` and `false`.
  - Objects: shallow objects (`{"item":"widget","count":5}`) and deeply nested structures (`{"user":{"id":1,"active":true,"tags":["a","b"]}}`).
  - Arrays: empty array (`[]`) and mixed arrays (`[1, "two", false, null]`).
- **Multi-queue isolation**: Enqueued an item to a separate queue (`notifications`). Verified that `GET /queues` returned both active queues and that operations on `orders` did not affect `notifications`.
- **Non-mutating inspections**: Verified `GET /peek/orders`, `HEAD /peek/orders`, and `HEAD /dequeue/orders` returned `200 OK` without consuming items or altering the queue length.
- **Strict FIFO ordering**: Dequeued all 18 items sequentially, asserting that each item emerged in the exact order enqueued with 100% value and type fidelity.
- **Empty queue draining & pruning**: Dequeued from empty `orders`, verifying `204 No Content` with no body, and verified that `orders` was automatically pruned from `GET /queues`. Drained `notifications` and confirmed `GET /queues` returned `[]`.

### 2. Protocol, Validation, Authentication, Limits & Error Paths

- **Authentication enforcement**: Confirmed that unauthenticated requests to protected endpoints return `401 Unauthorized` with the required `WWW-Authenticate: Bearer` challenge. Verified that valid tokens authenticate regardless of scheme casing (`bearer`, `Bearer`, `BEARER`) or whitespace formatting between scheme and token (single space, multiple spaces, tabs).
- **HTTP method routing (RFC 9110 §15.5.6)**: Verified that sending unsupported HTTP methods returns `405 Method Not Allowed` with the exact `Allow` header matching supported methods (`POST /health` -> `Allow: GET`, `GET /enqueue/q` -> `Allow: POST`, `POST /dequeue/q` -> `Allow: GET`, etc.).
- **Route 404s**: Verified that unrouted paths (`/unknown-path`, `/enqueue`, `/enqueue/`) return `404 Not found.`.
- **Payload validation**:
  - Empty body and malformed JSON return `400 Invalid JSON`.
  - Non-object bodies (`123`, `[]`) or objects missing the required `"payload"` key return `400 Missing payload key`.
  - Top-level `null` payloads (`{"payload":null}`) return `400 Null payload not allowed`.
  - Unsafe numbers exceeding IEEE 754 precision (`9007199254740993`) and overflow numbers (`1e309` / `Infinity`) return `400 Payload contains an unsupported number`.
- **Queue name limits**: 128 Unicode characters accepted; 129 characters rejected with `400 Queue name too long`. Malformed percent encodings (`%ZZ`) return `400 Invalid queue name`.
- **Body size limits**: Verified that bodies of exactly 1 MB (1,048,576 bytes) are accepted with `200 OK`, while bodies exceeding 1 MB (1,048,577 bytes) are rejected with `413 Payload too large` (both for fixed `Content-Length` and chunked streaming bodies).
- **Queue capacity limits**:
  - `QUEUE_DEPTH_LIMIT=3`: Enqueued 3 items; 4th item returned `507 Queue full or too many queues`. Dequeueing 1 item freed capacity and allowed immediate re-enqueue.
  - `QUEUE_COUNT_LIMIT=2`: Created 2 queues; 3rd queue returned `507 Queue full or too many queues`. Fully draining 1 queue freed capacity and allowed creating a new queue.
- **Rate limiting**: Configured `RATE_LIMIT_REQUESTS=5`; requests 1–5 returned `200 OK`, request 6 returned `429 Too many requests`. Verified `/health` bypassed the rate limiter and remained responsive (`200 OK`).

### 3. Persistence, Clean Restarts & Crash Recovery

- **Part A (Clean shutdown and recovery)**:
  - Started server with `--persist` and an isolated temporary directory.
  - Enqueued items across queues `p1` and `p2`, dequeued one item, and initiated a graceful `SIGTERM` shutdown.
  - Verified `persist.dat` snapshot on disk contained only remaining active items (`beta` on `p1`, `gamma` on `p2`).
  - Started a second clean server pointing to the same persist directory. Verified that active queues, lengths, and FIFO ordering were restored cleanly, and that draining queues left an empty snapshot.
- **Part B (Crash recovery / unclean shutdown with unchanged limits)**:
  - Started server with `--persist` and an isolated directory.
  - Enqueued 3 items to queue `tasks` (`task-1`, `task-2`, `task-3`) and dequeued `task-1`.
  - Sent `SIGKILL` to simulate an unhandled crash / power failure without graceful `save()`.
  - Verified `persist.dat` retained the raw 4-line transaction log (3 enqueues + 1 dequeue).
  - Started a recovery server against the same directory with identical limits. Confirmed that `tasks` was recovered with length 2 and that subsequent dequeues returned `task-2`, `task-3`, and then `204 No Content`.

### 4. Concurrency, URL Encoding & Boundary Edge Cases

- **Concurrent enqueue & dequeue**: Sent 30 parallel `POST /enqueue` requests to `concurrent-q`, followed by 30 parallel `GET /dequeue` requests. Verified all 30 enqueues returned 200, length reported 30, and all 30 distinct items were dequeued without drops or duplicates.
- **URL Percent Encoding**: Verified behavior with special characters in queue names:
  - Spaces (`my%20queue`): correctly enqueued, inspected, and dequeued as `"my queue"`.
  - Literal plus (`plus+test`) and encoded plus (`plus%2Btest`): both resolve to queue `plus+test`.
  - Encoded slashes (`sub%2Fqueue`): correctly isolated as queue `"sub/queue"` and survived enqueue, listing, and dequeue.
  - Encoded hashes (`hash%23test`): correctly resolved to queue `"hash#test"` without being clipped as a URL fragment.

## Confirmed finding

### [#106 — QUEUE_API_TOKEN with internal tabs or multiple spaces is accepted at startup and permanently locks out authenticated endpoints](https://github.com/jonbaldie/queue/issues/106)

- **User impact**: When `QUEUE_API_TOKEN` is configured with internal whitespace such as tabs (`\t`), multiple spaces, or newlines, the server starts up cleanly and reports healthy on `/health`. However, all requests to any authenticated endpoint (`/queues`, `/enqueue/:queue`, `/dequeue/:queue`, `/peek/:queue`, `/length/:queue`) are permanently rejected with `401 Unauthorized` regardless of client credentials. The server is completely inoperative for authenticated consumers while falsely appearing healthy to orchestration probes.
- **Root cause**: `parseConfig` in `src/config.ts` only trims outer padding (`value?.trim()`), accepting tokens with internal whitespace. In `src/middleware.ts`, `withAuth` parses credentials by splitting on `/\s+/` and rejoining with single spaces (`rest.join(" ")`). Incoming tokens can never contain tabs, newlines, or multiple spaces, making `token === trimmedToken` impossible.
- **Replay & Evidence**: Verified across 3 consecutive clean server instances with 100% recurrence. See [internal-whitespace-token-lockout-replay.txt](./internal-whitespace-token-lockout-replay.txt) and [token-internal-whitespace-replay.ts](./token-internal-whitespace-replay.ts).
