# Queue exploratory-testing report — 2026-10-17

## Outcome

Three confirmed bugs:

- [#174](https://github.com/jonbaldie/queue/issues/174): the README Docker `--persist` command (`PERSIST=/mnt/`) still exits 1 before listening. Same failure as closed #114.
- [#173](https://github.com/jonbaldie/queue/issues/173): a second server on the same `PERSIST` directory dequeues an item the first server also dequeues, and its shutdown snapshot can erase an item the second server already acknowledged.
- [#172](https://github.com/jonbaldie/queue/issues/172): an enqueue whose client closes before `Content-Length` bytes arrive is reported as `413 Payload too large`.

A single server's publish/consume path, graceful and `SIGKILL` restart with `--persist`, and a Docker named volume at `/data` behaved as documented.

## Journeys

### 1. Publish jobs and have workers consume them

Goal: a publisher enqueues jobs, a worker peeks without taking, then dequeue returns each job once, in order, as JSON. A bad publish can be corrected and retried. Empty dequeue is `204`.

Ordinary path, compiled binary, default limits, no `--persist`, `127.0.0.1:18771`.

- Health `200` without a token. Wrong token on dequeue `401` with `WWW-Authenticate: Bearer`, then the right token dequeued the same job.
- Invalid JSON and a missing `payload` key returned `400` and queued nothing. The corrected publishes returned `200`.
- Objects, `false`, `0`, `"0"`, `""`, and `[]` came back distinct and in order.
- Peek did not change length. After the last dequeue, `GET /queues` no longer listed that queue.
- Variation, four concurrent workers, 20 jobs: 20 unique deliveries, order preserved, then `204`.
- Variation, `HEAD /dequeue` did not consume the item. A later `GET` returned it.
- Percent-encoded space, slash, and `メール` round-tripped as one queue each. A 128-character name was accepted; 129 was `400`.
- `GET /enqueue` and `POST /dequeue` were `405` with an `Allow` header.
- A raw body `{"payload":9007199254740993}` was `400` and did not change length. `9007199254740991`, `1.0`, and `1e2` came back as `9007199254740991`, `1`, and `100`.

Evidence: [journey1_workers.ts](./journey1_workers.ts), [journey1-transcript.txt](./journey1-transcript.txt), [journey1_variation.ts](./journey1_variation.ts), [journey1-variation.txt](./journey1-variation.txt), [journey1-number-probe.txt](./journey1-number-probe.txt).

### 2. Remember acknowledged jobs across a restart

Goal: with `--persist`, items acknowledged with `200` and not yet dequeued are still there after the server is turned off, in order. A dequeued item does not come back.

Ordinary path: enqueue on `email`, `billing`, and `notes` (including `false`, `0`, `""`, and `こんにちは`), dequeue one email, `SIGTERM`, restart.

- Remaining email was `email-2`. Billing came back `false`, `0`, `""`. Notes came back `こんにちは`. Then `204` and `/queues` was `[]`.
- Shutdown log: `Flushing data to persist.dat...` and `Goodbye!`

Variation, `SIGKILL` after three enqueues and one dequeue: restart length was 2, deliveries were `{"n":2}` then `{"n":3}`, then `204`.

Variation, two `SIGINT`s while a client held an incomplete request: both acknowledged items survived the restart. The held request was logged as `413` (see #172). Not a separate data-loss bug.

Variation, `QUEUE_DEPTH_LIMIT=2` and `QUEUE_COUNT_LIMIT=2`: the third item and the third queue were `507`. Dequeue made room and the retry was `200`. Eight parallel enqueues at the depth limit returned only `200` or `507`, and length stayed 2.

A 1 MiB body was `200`. A body one byte over was `413` via curl, and length stayed 0. Python's `urlopen` reported connection reset while still uploading that body; the server log for that attempt was `413`. The reset was the client, not a missing `413`.

Evidence: [journey2_persist.sh](./journey2_persist.sh), [journey2-transcript.txt](./journey2-transcript.txt), [journey2_variations.sh](./journey2_variations.sh), [journey2-variations.txt](./journey2-variations.txt), [journey-limits.txt](./journey-limits.txt), [replay_findings.py](./replay_findings.py), [replay-findings.txt](./replay-findings.txt).

## Confirmed bugs

### #174 — documented Docker persist command does not start

User impact: copying the persistency `docker run` command produces a container that exits 1. Nothing listens.

Starting conditions: image built from this commit's `Dockerfile`, `PERSIST=/mnt/`, command from the README, host port 18791 mapped to container 1991.

Replay: [journey3-mnt.txt](./journey3-mnt.txt), then [journey3-mnt-run2.txt](./journey3-mnt-run2.txt).

Expected: the server logs `Listening` and accepts the token.

Actual: `Exited (1)`, `PermissionDenied` opening `/mnt/persist.dat.tmp`. Host `curl` could not connect. 2/2 runs.

### #173 — two servers, one persist directory

User impact: the same job is delivered twice, and a job acknowledged with `200` can be gone after the processes stop.

Starting conditions: empty `PERSIST` directory, two compiled binaries, ports 18781 and 18782, `--persist`.

Replay: [replay_findings.py](./replay_findings.py) `two_writers`, transcript [replay-findings.txt](./replay-findings.txt). An earlier pass is in [journey2-variations.txt](./journey2-variations.txt).

Expected: `"from-a"` delivered once. `"from-b"` still available after both processes stop.

Actual, 2/2 replay runs: both servers dequeued `"from-a"`. After `SIGTERM` of the first server and `SIGKILL` of the second, `persist.dat` was empty, restart length was `0`, dequeue was `204`. `"from-b"` was never delivered.

### #172 — aborted enqueue reported as too large

User impact: a publisher whose connection closes mid-body is told the payload is too large. A client that does not retry `413` never queues the job.

Starting conditions: server listening, `Content-Length: 40`, body `{"payload":`, write side half-closed.

Replay: [replay_findings.py](./replay_findings.py) `truncated_upload`, transcript [replay-findings.txt](./replay-findings.txt).

Expected: `400` or a connection error. OpenAPI reserves `413` for a payload over 1 MB.

Actual, 2/2 runs: `413` body `Payload too large`. Length stayed `0`. A complete retry was `200` and dequeued `"retry-ok"`.

## Rejected candidates

- Raw unsafe integer `9007199254740993`: `400`, length unchanged. An earlier `200` for that number was the driver calling `JSON.stringify` on a JavaScript number, which had already rounded it. Not a server bug.
- `HEAD /dequeue` consuming items: length stayed 1, then `GET` returned the item.
- Parallel enqueues at `QUEUE_DEPTH_LIMIT=2`: no `500`, length stayed 2.
- Oversize body via curl: `413`, item not queued. The Python connection reset happened while the client was still uploading after the server had already answered `413`.
- Double `SIGINT` during shutdown: both acknowledged items survived.
- `http://[::1]` connection refused: the README says the default bind is `127.0.0.1`. `http://localhost:18771/health` still returned `200`.

## Unresolved

## Usability observations

- After the last dequeue, the queue name disappears from `GET /queues`. OpenAPI says "active" queue names, so this matches the spec. An operator watching the list cannot see a drained queue. *Suggestion:* say in the README that a queue leaves the list when it becomes empty.
- The README quick start does not mention the default 100 requests/minute per client IP. This pass stayed under that budget, so it was not re-measured. The 2026-10-10 report still describes what a busy publisher and polling workers see.
- The image sets `PERSIST=/data/` and declares a `/data` volume, but the default command has no `--persist`. This pass did not re-run that combination. The README already says persistency is opt-in; the `/mnt/` command block is the part that fails (#174).

## Limitations and unexplored areas

- Docker was the image built from this commit, not the published `jonbaldie/queue` tag.
- Not explored: rate-limit recovery after a full minute, two containers publishing one host port (the second cannot bind), and a machine crash as opposed to process `SIGKILL`.
- The UTF-8 BOM prefix on an otherwise valid body was accepted with `200`. The stored payload was not read back. Not treated as a finding.
