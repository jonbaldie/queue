# Queue exploratory-testing report — 2026-10-10

## Outcome

Two confirmed bugs, both in `--persist` mode when the `PERSIST` volume runs out
of space. Both cause loss of items the API acknowledged with `200`:

- [#160](https://github.com/jonbaldie/queue/issues/160): short writes are
  treated as success and corrupt `persist.dat`. Acknowledged items are lost after
  a crash restart, or by a graceful shutdown that exits 0.
- [#161](https://github.com/jonbaldie/queue/issues/161): enqueue and dequeue
  return `500` when the persist write fails, but the in-memory queue has already
  changed. Rejected items are delivered later, and dequeued items vanish.

The ordinary worker flow and Docker volume recreation behaved as documented.

## Journeys

### 1. Publishers and polling workers (compiled binary, default config)

Goal: 3 producers enqueue 120 jobs while 3 polling workers drain the queue.
Every job is delivered exactly once, in order per producer.

- Default config: 99 `200`, 94 `429`. Only 41 of 120 jobs were enqueued and
  delivered. Producers on the same host share the default 100 requests/minute
  per-IP budget, and polling consumers spend it too.
- Variation, `RATE_LIMIT_REQUESTS=100000`: 120 sent, 120 received, 0 duplicates,
  per-producer order kept, final length 0.
- Requests with the wrong token also use up the budget (they get `429` before
  auth runs). The `429` response has no `Retry-After` header.

### 2. Persistence when the `PERSIST` volume fills up (compiled binary)

Goal: items acknowledged with `200` under `--persist` survive a restart. A full
disk should cause visible failures, not silent loss.

- Crash after a disk-full episode: 3 items acknowledged, 1 recovered after
  SIGKILL (2/2 runs). **Confirmed, #160.**
- Variation, graceful SIGTERM after the same episode: all 3 recovered (1/1 run).
  The snapshot is rebuilt from memory.
- Graceful SIGTERM with about 100 KiB free: exit 0 and `Goodbye!`, but
  `persist.dat` drops from 200123 to 4096 bytes. 1 of 2 items recovered (2/2
  runs). **Confirmed, #160.**
- Disk completely full: `500` enqueues still add the item (length 5 when 2 were
  accepted). Each `500` dequeue removes an item (length 5 → 4 → 3). After space
  returns, the 3 rejected items are delivered and the 2 accepted ones never are
  (2/2 runs). **Confirmed, #161.**

### 3. Docker deployment per README

Goal: the README's Docker `--persist` command with a named volume keeps items
across container *recreation*.

- 3a: enqueue 2 items, dequeue 1, `docker rm -f`, recreate with the same volume.
  Length 1, the remaining item was delivered, then `204`. Pass.
- 3b: the default `CMD` (no `--persist`) with `-v ...:/data` loses items across
  restart. This matches "Persistency is opt-in", so it is not a bug. See the
  usability notes.
- 3c: graceful `docker stop` with a nearly full 2 MiB tmpfs `/data`. Exit 0, and
  `persist.dat` drops from 200123 to 102400 bytes. 1 of 2 items recovered. This
  reproduces #160 on Linux.

## Rejected candidates

- In runs 1–2 of `journey2_enospc_500.sh`, `/length` returned `Internal Server
  Error` after a failed dequeue. Cause: the harness wrote the server log onto the
  full volume, so the log write failed. Runs 3–4 kept the log elsewhere and
  `/length` worked. This is a harness artifact and is annotated in the transcript.

## Usability observations

- The README does not mention the rate limit (`RATE_LIMIT_REQUESTS`, default 100
  requests/minute per client IP), `QUEUE_DEPTH_LIMIT`, `QUEUE_COUNT_LIMIT`,
  `/peek`, or `/queues`. A single-host setup that follows the README's
  publisher/subscriber advice hits `429` within a minute (journey 1).
  *Suggestion:* document these in the README and add `Retry-After` to `429`.
- The image sets `PERSIST=/data/` and declares a `/data` volume, but the default
  `CMD` has no `--persist`. Mounting a volume therefore persists nothing
  (journey 3b). The README's "Mount a named volume there" sentence does not
  repeat that `--persist` is required. *Suggestion:* say so in that sentence.
- The README calls `persist.dat` a "binary log", but it is newline-delimited JSON.

## Limitations and unexplored areas

- Disk-full was simulated with RAM disks and tmpfs, not with a real full disk.
  Short-write sizes depend on the filesystem (4096 B on HFS+, 102400 B on tmpfs).
- Docker Desktop port mapping makes host clients share one source IP. How that
  affects per-IP rate limits behind a real NAT was not measured.
- Not explored this pass: concurrent server instances sharing one `PERSIST`
  directory, and signal storms during shutdown.
