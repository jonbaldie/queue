## Journeys and outcomes

### 1. Publish and consume typed work

**Goal:** preserve JSON types and FIFO order while independent workers consume each job once, matching the README's queue contract.

- Enqueued and dequeued string `"0"`, number `0`, boolean `false`, empty arrays/objects, nested null/boolean fields, Unicode text, and a NUL-containing string on a Unicode-named queue. Observed exact decoded values in FIFO order.
- `HEAD /dequeue` returned no body and did not reduce length; `peek` returned the oldest item without consuming it.
- Six concurrent consumers received all 120 unique jobs exactly once. The queue length was zero afterward, and drained queues disappeared from `/queues`.
- Confirmed unauthenticated queue access returns 401 while public health remains available.

Evidence: [journeys.txt](journeys.txt), [j1-server.log](j1-server.log).

### 2. Recover queued work after restart

**Goal:** preserve remaining jobs, not resurrect consumed work, and safely reject another process using the same persistence directory.

- Published five object jobs and consumed one. A second process using that directory failed before listening, reporting `PersistDirectoryInUseError` / “already in use”; the original process continued serving.
- Repeated with both graceful SIGTERM and abrupt SIGKILL. Restarted with queue depth/count limits reduced to one; all four remaining jobs survived despite exceeding the new depth limit, in original order. Additional enqueue returned 507.
- Drained the queue, published to a new queue, restarted again, and retrieved that new job. Already-consumed jobs did not reappear. Both restart modes also demonstrated lock release after process exit.

Evidence: [journeys.txt](journeys.txt), [graceful restart log](j2-0-restart-server.log), [crash restart log](j2-1-restart-server.log), [rival rejection](j2-1-rival-server.log).

### 3. Correct invalid input and exercise boundaries

**Goal:** reject invalid or oversized input without mutating queues, accept documented boundaries, and allow retries when capacity becomes available.

- Invalid JSON, missing/null payloads, lossy integer `9007199254740993`, `1e400`, malformed UTF-8, malformed queue-name encoding, and excess nesting returned 400. Invalid payloads created no queue.
- A 128-code-point emoji queue name was accepted; 129 code points returned 400.
- Depth limit two and queue-count limit two returned 507 without phantom queues or replacing existing jobs. Retrying after draining an item/queue succeeded, with the expected payload delivered afterward.
- An exactly 1,048,576-byte request succeeded and its full payload was retrieved. A 1,048,577-byte request returned 413 and did not increase the queue length.
- Persistent object payloads nested 1,000, 2,000, and 2,999 levels (plus the request envelope) were accepted. Peek and dequeue after restart matched the exact expected bytes. Repeated from two fresh directories.
- With three requests/minute, observed 200, 200, 200, 429; health still returned 200. After a real 61-second wait, queue access returned 200 again. No clock replacement or mocks.

Evidence: [journeys.txt](journeys.txt), [j3-server.log](j3-server.log), [deep payload server](j3-depth-0-server.log), [deep payload restart](j3-depth-0-restart-server.log), [rate server](j3-rate-server.log).

## Evidence boundary

The three journey functions in [driver.py](driver.py) are production-grounded: assertions observe HTTP responses from the service, process exit/log diagnostics, or data retrieved through HTTP after restart. No fake queue/store/server is used. Classification counts: **3 production-grounded journeys, 0 test-layer-only, 0 unclear, 0 wholly test-local journeys**. The two `len(raw)` size checks are test-local fixture guards, not evidence of service behaviour; the paired response and retrieval checks supply that evidence. Deep-payload byte/hash output is supplemented by actual byte-equality assertions before and after restart.

Usability observation: the API's 507 response does not distinguish exhausted queue depth from exhausted queue count. In these journeys, `/length` and `/queues` made the cause observable; a more specific diagnostic could help clients, but this is not filed as a bug.
